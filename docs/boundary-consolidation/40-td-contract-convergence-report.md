## 2. Canonical artifact decisions

### 2.1 Hash semantics

Every generated consumer artifact uses the same rule:

- `content_hash` = `sha256:` over canonical JSON (sorted keys, no whitespace,
  ASCII escaping) of the document **excluding `content_hash`**; this is the
  artifact self-hash.
- The source declaration hash is stored separately: devices uses
  `source_hash`; scenarios uses `provenance.scenario_content_hash`.
- A consumer recomputes the self-hash and rejects a stale/edited artifact
  (`STALE_DEVICE_HASH`, `STALE_SCENARIO_HASH`, or devices' `STALE_SNAPSHOT`).
- Pins compare `source_hash` (devices) or the scenario provenance hash; they
  do not pin the artifact self-hash to the source.

### 2.2 Device snapshot `jcheng.device_snapshot.v1`

- `source_hash` — profile content hash.
- `content_hash` — artifact self-hash.
- `attributes` — `{category, role, dof, control_modes, kinematics_declared}`,
  plus `data_status` only when the source declares it.
- `dof` is `null` when kinematics are not declared. A 7-axis arm with no
  recorded kinematics therefore reports `null`, not `7`.
- Capabilities keep native interface IDs (`arm.position_control`,
  `end_effector.position_control`, `sensor.rgb_stream`, ...).
- No `reach_m`, `payload_kg`, `aperture_m` or camera resolution is invented.

### 2.3 Scenario requirements `jcheng.scenario_requirements.v1`

Device requirement:

```yaml
id: manipulation.arm.dof
requirement_id: arm_dof
requirement_owner: device
role: arm
interface: arm.position_control
required: true
threshold: {op: ">=", value: 4, unit: joints}
statement: ">= 4 independently commanded joints"
verification: Unverified
```

Algorithm requirement:

```yaml
id: perception.scene_state
requirement_id: scene_state
requirement_owner: algorithm
required: true
deferred_to: jcheng-perception
statement: Advisory scene state with validity, freshness and explicit unknowns.
verification: Unverified
```

`threshold` is optional. A requirement with no numeric threshold (for example
camera resolution stated as width × height) stays prose and is classified
`unverified`, never promoted.

### 2.4 Matching outcomes

| Outcome | Meaning |
|---|---|
| `matched` | Declared interface present and a declared device fact meets the threshold; evidence level still recorded. |
| `matched_with_unverified` | At least one fact matched and at least one requirement has no declared fact/threshold. |
| `unverified` | No device fact could be matched. |
| `deferred` | Algorithm-owned requirement; not matched against a device. |
| fail closed | Missing role, missing required interface, or a threshold mismatch. |

Only `matched` sets `deployable: true`. A mock run can proceed on
`matched_with_unverified` because it is explicitly labelled and executes no
hardware; it does not claim task success.
