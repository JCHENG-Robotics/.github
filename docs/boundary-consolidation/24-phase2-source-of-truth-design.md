# Phase 2 Design — Device and Scenario Sources of Truth

> Status: **design only (2026-11-27)**. Implementation is gated on this round's
> approved PR merges, cross-repository regression and independent QA. No source
> files were migrated and no device/scenario consumer was changed in this
> round.

## 1. Scope

MIG-01 (devices) and MIG-02 (scenarios) with **ArmPi Ultra × ore_sorting** as
the first offline vertical. No second arm, no second scenario, no real-ore
grasp, no hardware.

## 2. MIG-01 — Device source of truth

### 2.1 Identity and content

| Field | Definition | Owner |
|---|---|---|
| `device_id` | Stable ID, e.g. `hiwonder.armpi-ultra` | devices |
| `device_version` | Profile semantic version | devices |
| `content_hash` | SHA-256 of canonicalized profile content | devices |
| `capability_profile` | Capability IDs + parameters (e.g. `arm.position_control`) | devices |
| `generated_snapshot` | Deployment-shaped copy for system/simulation/learning | consumer, generated from devices |
| `provenance` | `repo@commit`, source file, date, generator version | devices + consumer |
| `safety_overlay` | System-only tightening (limits, workspace, timing) | system |
| `compatibility validation` | Required capability vs available capability | devices + consumers |

### 2.2 Authority model

```text
devices registry (declarative truth)
  device_id + device_version + content_hash + capability_profile
        │  pinned reference (offline; no runtime call)
        ├── system generated_snapshot + safety_overlay
        ├── simulation plant reference (keeps plant-only parameters)
        ├── learning adapter reference
        ├── studio read-only display
        └── applications capability matching
```

Rules:

- Devices owns device **declarations**; system owns the **deployed instance**
  and safety overlay. System never requires devices online.
- A snapshot must carry `source_device`, `device_version`, `content_hash`,
  generator version and a timestamp; it is read-only and regenerated by a
  script.
- Overlapping fields must match after applying the system overlay; a mismatch
  is a release blocker, not a preference.
- Unknown, missing or incompatible capabilities are **rejected**; no default
  "assume deployable".
- The old handwritten profiles remain until equivalence is proven; no deletion
  in the first migration.

### 2.3 Compatibility validation

1. Load the device profile and compute `content_hash`.
2. Compare the pinned hash with the snapshot's `source_hash`.
3. Compare joint names, order, units, limits and capability IDs.
4. Apply the safety overlay; the stricter bound wins; a looser overlay is an
   error.
5. Check every required capability from the scenario against the device list;
   unknown → `INCOMPATIBLE_CAPABILITY`; parameter mismatch →
   `INCOMPATIBLE_PARAMETER`.
6. A stale snapshot (hash mismatch) is detected before planning.

### 2.4 Migration sequence

1. Add the ID/version/hash/provenance fields to the devices profile and a
   generator CLI; no consumer change yet.
2. Generate the ArmPi snapshot; diff it against the current system profile;
   record every difference (expected: safety overlay only).
3. Run system profile validation and the existing tests with the generated
   snapshot behind a config flag.
4. Dual-read: compare old and new values in CI; no runtime switch.
5. Switch the default only after equivalence and regression pass; retain the
   old file for one release; then deprecate it explicitly.
6. Only after the above, remove redundant handwritten copies (never directly
   delete first).

## 3. MIG-02 — Scenario source of truth

### 3.1 Identity and documents

| Field | Definition | Owner |
|---|---|---|
| `scenario_id` | Stable ID, e.g. `ore_sorting` | scenarios |
| `scenario_version` | Semantic version | scenarios |
| `task_specification` | Goal, preconditions, success/failure, constraints | scenarios |
| `capability_requirements` | Abstract device/algorithm requirements | scenarios |
| `operational_constraints` | Business/environment/risk constraints | scenarios |
| `evaluation_specification` | Metrics, data sources, protocol | scenarios |
| `evaluation_id` | Stable evaluation ID + version | scenarios |

### 3.2 Consumer contracts

| Consumer | Consumes | Does not own |
|---|---|---|
| applications | task spec + constraints → recipe/plan | success thresholds, safety limits |
| simulation | environment profile → world assets | task success, evaluation results |
| benchmark | evaluation spec → suite/report | task semantics, thresholds |
| devices | capability requirements → capability match | scenario acceptance |
| perception | semantic profile (advisory) | task phase, success |
| system | safety boundary only | business task, evaluation |

Rules:

- No safety judgment migrates to scenarios; system safety remains independent.
- Perception `scene_state`/`Phase` is not a task state; any task-phase decision
  stays in applications/scenarios.
- A recipe references `scenario_id@version` and `task_id@version`; a benchmark
  suite references `evaluation_id@version`.
- Unknown scenario/version or an incompatible device capability → reject, not
  warn-and-continue.

### 3.3 Migration sequence

1. Add stable `scenario_id`/`scenario_version` and `evaluation_id` to the
   ore_sorting reference; keep current schema.
2. Add optional `scenario_ref`/`evaluation_ref` to recipes/suites (repo-local
   fields; no interfaces contract change).
3. Add a read-only compatibility checker: scenario requirements vs device
   capabilities.
4. Simulation loads the environment profile behind a flag; no asset rewrite.
5. Benchmark loads the evaluation spec behind a flag; thresholds stay empty
   until a baseline exists.
6. Keep the old duplicated definitions until equivalence is proven; no deletion.

## 4. ArmPi Ultra × ore_sorting reference integration

Offline flow:

```text
devices registry (ArmPi Ultra)
  + scenarios ore_sorting
  → capability match
  → applications recipe/plan
  → mock system gateway (lease/stop/limits)
  → simulation plant (domain 43, assets from environment profile)
  → benchmark suite/report (evaluation id/version, provenance)
```

Validation matrix:

| # | Check | Expected |
|---|---|---|
| 1 | Device profile loads | ID/version/hash resolved |
| 2 | Scenario loads | ID/version and all profiles resolve |
| 3 | Requirement ↔ capability match | exact match, no unknown |
| 4 | Unknown capability | explicit rejection |
| 5 | Incompatible parameter/version | explicit rejection |
| 6 | Task plan consumes scenario | plan records scenario/task version |
| 7 | Mock system executes | lease/stop/limits enforced, no hardware |
| 8 | Simulation consumes environment | same frames/stations, domain 43 only |
| 9 | Benchmark report | evaluation id/version + dataset hash + provenance |
| 10 | Device change / stale snapshot | hash mismatch detected |
| 11 | Scenario version change | incompatible consumer detected |

## 5. Contract policy

- Device and scenario schemas remain repo-local v1 until a second real consumer
  parses them. The first cross-repo consumer triggers an `jcheng-interfaces`
  proposal.
- The ArmPi×ore_sorting reference uses **pinned fixtures/snapshots** with
  provenance, not a new runtime contract.
- No IDL/schema/hash change in this design; a proposal is required before one.

## 6. Risks and rollback

| Risk | Mitigation |
|---|---|
| Snapshot drifts from devices | content hash + CI compare + stale detection |
| Safety overlay loosens a limit | stricter-wins rule; reject looser overlay |
| Scenario version breaks a consumer | explicit version ref + compatibility check |
| Duplicate logic during migration | dual-read/comparison; no deletion until equivalent |
| Circular dependency | offline pinned copies; no runtime import; B1 gate |
| Hidden hardware dependency | no device/DDS in the reference; mock only |

Rollback: disable the new flag, keep the old profile/recipe/suite, retain the
snapshot and its provenance; no history rewrite.

## 7. Implementation gate

Implementation starts only after:

1. the approved PRs are merged (or the Board accepts a documented subset);
2. post-merge integration regression passes;
3. independent QA passes the Phase 2 design/implementation.
